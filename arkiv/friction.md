# Integration friction

We expected a direct Rabdi RPC request to work with the endpoint alone. The public RPC rejected unauthenticated requests during setup. A server-side transport using a Rabdi-scoped Hub access key resolved the read. A separate funded writer and faucet verification were required for confirmed writes. The Worker sends `X-API-KEY` from its server configuration. [Transport implementation](../worker/src/adapters/arkiv.ts#L22) · [Arkiv Hub](https://hub.arkiv.network)

To check access, make a single `eth_chainId` request to the Rabdi RPC, then run a one-row case query with the filters shown in the [adapter](../worker/src/adapters/arkiv.ts#L127). On the latest check the keyless endpoint returned chain ID `7794095` (`0x76edaf`) and one matching row. The SDK warned about the rate limit on the public endpoint, so an unauthenticated failure from setup may not reproduce on a single call today. If a query fails under ordinary use, repeat that query with a valid Hub key in `X-API-KEY`. The [public case query](https://guardlink.ajnasnb.com/api/v1/transparency/?caseId=dfd3e4f9-9008-4e60-b420-f10ae15c5f81) exercises GuardLink's configured transport.

Publishing waits for individual chain confirmations. GuardLink limits a publish call to three events and prioritizes new archive references. A documented create, confirm and query example with the custom header and an explanation of transient index visibility would shorten this setup.
